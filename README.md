# OSM-Based Driver Assistance and Map Visualization for Autonomous Driving Applications

A ROS2 and Python workflow that uses OpenStreetMap route-analysis outputs, replays vehicle odometry from CSV, localizes the vehicle onto the OSM-derived route, generates driver-assistance alerts, and publishes route/vehicle visualization topics for tools such as Mapviz or RViz.

---

## Overview

This branch extends the OSM route-analysis pipeline into a driver-assistance and visualization system.

The workflow connects four main pieces:

- `osm_route_analysis.py` generates route-level and segment-level OSM intelligence.
- Precomputed route JSON files in `output/` provide road attributes, curvature, intersections, traffic controls, and segment geometry.
- CSV odometry data provides replayed vehicle position along the route.
- The ROS2 `driver_assistant` package publishes the route, vehicle pose, route markers, and alert text while also running a driver-facing alert interface.

The system is designed to demonstrate how OSM-derived map intelligence can support autonomous-vehicle and driver-assistance research, especially for rural routes where lane count, speed limits, curvature, intersection density, and upcoming road controls are useful contextual signals.

## Input Definition

The driver-assistance system uses two primary inputs.

### 1. OSM Route JSON

The route JSON is generated by `osm_route_analysis.py` and stored in `output/`.

Example:

```text
output/FM_1362_to_FM_2000.json
```

The driver-assistance system expects the JSON to contain:

| Key | Purpose |
|-----|---------|
| `route_metrics` | Total route length and travel-time estimate. |
| `edge_attributes` | Per-segment road attributes and geometry. |
| `intersection_details` | Intersection locations, control types, and route position. |
| `edge_attribute_summary` | Route-level average speed and aggregate road information. |
| `waypoint_density_summary` | Density statistics for route geometry. |
| `points_of_interest` | Signals, stops, crossings, bike lanes, and other nearby OSM features. |

Each segment in `edge_attributes` must include:

| Field | Description |
|-------|-------------|
| `segment_id` | Unique segment identifier. |
| `segment_geometry_wkt` | Segment polyline as WKT geometry. |
| `segment_start_m` | Cumulative distance at the start of the segment. |
| `segment_end_m` | Cumulative distance at the end of the segment. |
| `segment_length_m` | Segment length in meters. |
| `primary_highway` | OSM road classification. |
| `maxspeed_kph` | OSM or inferred speed limit. |
| `lanes_count` | OSM or inferred lane count. |
| `direction` | `oneway` or `twoway`. |
| `curvature_deg` | Bearing change relative to the previous segment. |
| `waypoint_density_per_km` | Segment geometry density. |
| `driving_state` | Structured segment state used for AV/CAV interpretation. |

### 2. Odometry CSV

The odometry CSV provides replayed vehicle positions.

Example:

```text
combined_novatel_odom_data.csv
```

Expected columns:

| Column | Description |
|--------|-------------|
| `timestamp` | Time associated with the odometry record. |
| `position_x` | Vehicle X position in projected metric coordinates. |
| `position_y` | Vehicle Y position in projected metric coordinates. |
| `position_z` | Vehicle Z position. |
| `orientation_x` | Quaternion x. |
| `orientation_y` | Quaternion y. |
| `orientation_z` | Quaternion z. |
| `orientation_w` | Quaternion w. |

The CSV coordinates must be in the same projected coordinate frame as the projected OSM route used by the matching logic. If the vehicle-to-route distance is unexpectedly large, the route CRS and CSV coordinate frame should be checked first.

## Core Features

### Vehicle-to-Route Localization

The driver-assistance node projects OSM segment geometries into a metric CRS and matches every CSV vehicle coordinate to the closest route segment.

For each odometry point, the system computes:

- nearest OSM route segment
- lateral distance from the vehicle to that segment
- distance along the matched segment
- cumulative distance along the full route
- remaining route distance
- estimated remaining travel time

This allows the alert system to follow the actual replayed vehicle location instead of simply stepping through route segments one-by-one.

### Segment Matching Logic

Each route segment is represented as a `LineString`. Each vehicle record is represented as a `Point`.

For a vehicle point `P` and route segment `L_i`, the nearest segment is selected by the smallest Euclidean distance:

```text
d_i = distance(P, L_i)
```

After the nearest segment is selected, the vehicle position is projected onto the segment:

```text
s = project(P onto L_i)
```

The full route progress is then computed as:

```text
distance_along_route_m = segment_start_m + distance_along_segment_m
```

This route-progress value is used for upcoming-intersection warnings, remaining-distance calculation, and verification.

### Driver Assistance Alert Logic

The main driver-assistance node classifies and displays road context from the matched OSM segment.

The displayed features include:

| Feature | Source |
|---------|--------|
| Current segment ID | Matched OSM segment. |
| Curvature state | `curvature_deg` from route analysis. |
| Road type | `primary_highway` classification. |
| Road direction | `direction` field. |
| Speed limit | `maxspeed_kph`. |
| Speed source | `speed_inference_source`. |
| Lane count | `lanes_count`. |
| Lane source | `lane_inference_source`. |
| Advisory speed | Derived from speed limit and curvature. |
| Upcoming intersection | `intersection_details` lookahead check. |
| Current segment control | Signal/stop check near current segment range. |
| Waypoint density | `waypoint_density_per_km`. |
| Remaining distance | Route length minus current route progress. |
| Remaining time | Remaining distance divided by average route speed. |

### Curvature Classification

Curvature is classified from `curvature_deg`:

| Curvature | Display State |
|-----------|---------------|
| `< 10 deg` | `Straight` |
| `10 – 30 deg` | `Moderate Curve` |
| `>= 30 deg` | `High Curvature` |

The GUI uses these states to show a simple curve symbol and alert level.

### Road Type Classification

Road type is converted into driver-facing categories:

| OSM highway value | Display Class |
|-------------------|---------------|
| `motorway`, `trunk`, `primary` | `Highway` |
| `secondary`, `tertiary` | `Rural/Arterial` |
| `residential`, `service`, `living_street` | `Residential` |
| other values | Title-cased OSM class |

### Speed Display and Advisory Speed

The system displays speed in mph.

If the speed comes directly from OSM, it is displayed as a normal speed limit. If the speed is inferred, the display includes an inferred marker.

Example:

```text
37.3 mph (inf)
```

Advisory speed is computed only when the speed source is direct OSM speed data.

| Curvature State | Advisory Rule |
|-----------------|---------------|
| `High Curvature` | `0.5 × speed limit` |
| `Moderate Curve` | `0.7 × speed limit` |
| `Straight` | unchanged speed limit |

The advisory speed is rounded to the nearest 5 km/h and displayed in mph.

### Upcoming Intersection Warning

The function checks `intersection_details` for intersections within a configurable lookahead window.

Default lookahead:

```text
150 m
```

Possible messages:

```text
Signalized intersection ahead in X mi
Stop-controlled intersection ahead in X mi
Intersection ahead in X mi
```

### Current Segment Control Check

The current segment is checked against nearby intersections using the segment distance interval:

```text
[segment_start_m, segment_end_m]
```

A default window of `40 m` is applied around the segment interval.

Possible results:

```text
Traffic signal on current segment
Stop-controlled intersection on current segment
None
```

### Route Verification

The driver-assistance node includes verification checks to confirm that the CSV replay is being matched correctly to the OSM route.

Verification fields include:

| Field | Meaning |
|-------|---------|
| `snap_distance_m` | Distance from vehicle point to nearest route segment. |
| `snap_ok` | Whether the vehicle is close enough to the route. |
| `progress_ok` | Whether route progress is moving forward. |
| `continuity_ok` | Whether segment transitions are reasonable. |
| `overall_ok` | Combined verification status. |
| `issues` | Human-readable verification problems. |

A large snap distance usually means the odometry CSV coordinate frame does not match the projected OSM route frame.

## ROS2 Topics

The ROS2 nodes publish the following topics.

| Topic | Message Type | Published By | Purpose |
|-------|--------------|--------------|---------|
| `/osm_route_path` | `nav_msgs/Path` | `driver_assistant_node`, `csv_mapviz_player` | Route polyline for Mapviz/RViz visualization. |
| `/osm_route_markers` | `visualization_msgs/MarkerArray` | `driver_assistant_node`, `csv_mapviz_player` | Intersection, stop, and signal markers. |
| `/vehicle/odom` | `nav_msgs/Odometry` | `driver_assistant_node`, `csv_mapviz_player` | Replayed vehicle pose from CSV. |
| `/driver_alert_text` | `std_msgs/String` | `driver_assistant_node`, `csv_mapviz_player` | Current driver-assistance alert text. |

## Map Visualization

The route and vehicle can be visualized in Mapviz or RViz using the ROS2 topics.

The visualization publishes:

- OSM route path as `/osm_route_path`
- vehicle odometry as `/vehicle/odom`
- intersection/control markers as `/osm_route_markers`
- driver alert text as `/driver_alert_text`

The Mapviz/RViz coordinate frame is `map`. The route and vehicle positions are shifted by the first odometry coordinate so the visualization starts near `(0, 0)` instead of large UTM coordinates.

### Marker Coloring

| Marker Type | Color Meaning |
|-------------|---------------|
| Signalized intersection | Yellow |
| Stop-controlled intersection | Red |
| Other intersection | Blue |

## How to Run the Driver Assistance System

### Option 1: Launch both ROS2 nodes

```bash

source install/setup.bash

  route_file:=/absolute/path/to/osm_loader/output/FM_1362_to_FM_2000.json \
  odom_csv:=/absolute/path/to/osm_loader/combined_novatel_odom_data.csv \
  publish_rate_hz:=10.0
```

This starts:

- `driver_assistant_node`
- `csv_mapviz_player`

```bash
ros2 run driver_assistant driver_assistant_node \
```

```bash
ros2 launch driver_assistant driver_assistant_launch.py \
```

Add displays for:

| Mapviz Display | Topic |

| MarkerArray | `/osm_route_markers` |

```bash
ros2 topic list

```

## Notes and Assumptions

- The driver-assistance system depends on route JSON files that include segment geometry and cumulative segment distance fields.
- The odometry CSV must use a compatible projected coordinate frame with the projected route geometry.
- If `/vehicle/odom` publishes but the vehicle is not visible in Mapviz, check the fixed frame and display settings first.
- If the snap distance is large, check coordinate-frame alignment between the odometry CSV and OSM route projection.
- Inferred speeds and lanes are displayed separately from OSM-provided values so the user can distinguish measured map data from estimated data.
- The system is intended as a research prototype for OSM-based driver assistance and AV/CAV context extraction, not as a production safety system.

## Typical Workflow

```text
1. Run osm_route_analysis.py to generate route JSON.
2. Load the route JSON and odometry CSV in the ROS2 driver-assistance node.
3. Project OSM segment geometries into metric coordinates.
4. Match each CSV vehicle coordinate to the nearest route segment.
5. Extract current OSM segment features.
6. Compute curve, control, speed, density, remaining-distance, and intersection alerts.
7. Display the driver alert GUI.
8. Publish ROS2 topics for Mapviz/RViz visualization.
9. Save the driver-state table to output/driver_state_table_segment_only.csv.
```

## Current Branch Purpose

This branch demonstrates a driver-assistance layer built on top of the OSM route-analysis outputs.

The main contribution is the connection between:

- OSM-derived route intelligence
- replayed vehicle odometry
- segment-level vehicle localization
- driver-facing alert logic
- ROS2 topic publishing for visualization

This makes the OSM data usable not only as an offline map-analysis output, but also as a live-style driver-assistance input that can be connected to vehicle odometry, Mapviz, and future autonomous-driving modules.
